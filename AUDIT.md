# CodeCompass Audit

**Date:** 2026-11-06  
**Scope:** Spring Boot API, Vite frontend, indexing and retrieval pipeline, persistence, configuration, security boundaries, and deployment readiness.

## Summary

CodeCompass builds successfully and its health endpoint responds. Its local, single-user workflow is viable, but the current API and persistence model are not suitable for public or multi-user deployment. The most serious issues are unrestricted filesystem indexing, a shared mutable index, stale-index reuse, and non-atomic replacement of the active index.

## Findings

### Critical — Unauthenticated arbitrary filesystem indexing

`POST /api/index` accepts a caller-provided path and resolves it directly on the host filesystem.

- Evidence: `src/main/java/dev/codecompass/api/AssistantController.java:21-24`
- Evidence: `src/main/java/dev/codecompass/indexing/RepositoryPathResolver.java:11-21`
- Impact: A publicly exposed server could be instructed to index source readable by its service account, then return information from that source through Q&A. This also conflicts with a hosted workflow in which users submit repository links.
- Recommendation: Replace filesystem paths with a controlled repository-ingestion service. Authenticate users, restrict repository providers and clone destinations, and run cloning/indexing in an isolated workspace.

### High — One mutable index is shared by all repositories and users

The vector store, BM25 corpus, and state record are each single files. A new index deletes and replaces the active vector data, and `/api/ask` has no repository identifier.

- Evidence: `src/main/java/dev/codecompass/indexing/RepositoryIndexer.java:71-79`
- Evidence: `src/main/java/dev/codecompass/config/VectorStoreConfiguration.java:16-21`
- Evidence: `src/main/java/dev/codecompass/indexing/KeywordIndexStore.java:26-45`
- Impact: Indexing another repository replaces the prior repository. In a hosted deployment, users could receive answers from another user's repository.
- Recommendation: Introduce repository IDs and ownership. Persist a separate index per repository, or use a vector database with repository and owner filters.

### High — Reuse does not detect source or embedding changes

Existing indexes are reused when the repository path and index version match. The saved state does not record a source revision, file fingerprint, embedding model, or embedding dimensions.

- Evidence: `src/main/java/dev/codecompass/indexing/RepositoryIndexer.java:50-58`
- Evidence: `src/main/java/dev/codecompass/indexing/RepositoryIndexStateStore.java:33`
- Impact: Source edits can leave answers based on old code. Changing `OLLAMA_EMBEDDING_MODEL` can reuse vectors generated by a different model.
- Recommendation: Store the Git commit when available, a deterministic content fingerprint otherwise, and embedding/chunking configuration metadata. Reindex when any differ.

### High — Index replacement is non-atomic and concurrent requests are unsafe

The existing vector index is deleted before replacement embeddings complete. Vector, keyword, and state files are written independently, and there is no lock around indexing or retrieval.

- Evidence: `src/main/java/dev/codecompass/indexing/RepositoryIndexer.java:71-79`
- Impact: A failed embedding request can leave an empty or partially rebuilt active index. Concurrent indexes can race, and Q&A can read inconsistent vector and keyword data.
- Recommendation: Build a complete staged index in a temporary location, validate it, then atomically swap an immutable repository version into service. Serialize indexing per repository and retain the previous successful index until replacement succeeds.

### Medium — Repository ignore files can re-include secrets

Built-in patterns initially exclude common secret files, but later `.gitignore` or `.codecompassignore` matches can override that decision.

- Evidence: `src/main/java/dev/codecompass/indexing/RepositoryIgnoreRules.java:22-25`
- Evidence: `src/main/java/dev/codecompass/indexing/RepositoryIgnoreRules.java:40-46`
- Impact: A repository rule such as `!.env` can cause credentials to be indexed. If Gemini is selected, retrieved excerpts can then leave the host.
- Recommendation: Apply non-overridable secret exclusions after repository-specific rules. Maintain an explicit deny-list for credentials and private-key formats.

### Medium — Some generated dependency directories are not excluded

Directory names are lowercased before matching, but the ignore set contains `Pods`, `Carthage`, and `DerivedData` with uppercase letters.

- Evidence: `src/main/java/dev/codecompass/indexing/RepositoryIgnoreRules.java:38`
- Evidence: `src/main/java/dev/codecompass/indexing/RepositoryIgnoreRules.java:65`
- Impact: Those directories can be traversed and increase indexing time and resource usage.
- Recommendation: Store every ignored directory name in lowercase, or compare with a case-insensitive collection.

### Medium — Indexing and provider calls run synchronously without explicit timeouts

Indexing, local embedding, and Q&A run in HTTP request threads. Gemini calls do not configure connect or read timeouts.

- Evidence: `src/main/java/dev/codecompass/api/AssistantController.java:21-29`
- Evidence: `src/main/java/dev/codecompass/qa/GeminiAnswerClient.java:36-42`
- Impact: Larger repositories can exceed browser or proxy timeouts and consume request threads. An unavailable provider can leave requests blocked for too long.
- Recommendation: Move cloning and indexing to bounded background jobs with progress/status endpoints. Configure connection, read, and total request timeouts plus retries where safe.

### Medium — Source references do not guarantee claim-level grounding

When a model omits citations, the application appends references based on topic overlap rather than proving each claim is supported by the referenced source.

- Evidence: `src/main/java/dev/codecompass/qa/RagPipeline.java:47-54`
- Evidence: `src/main/java/dev/codecompass/qa/RagEvidenceGuard.java:30-48`
- Impact: A detailed but partially unsupported answer can look fully cited.
- Recommendation: Keep model citations separate from retrieval references, show the latter as “retrieved sources,” and add evaluation cases that score answer entailment against sources.

### Medium — Retrieved code remains a prompt-injection input

The system prompt tells models to treat repository text as untrusted, but arbitrary source comments and documentation are still included in the model prompt.

- Evidence: `src/main/java/dev/codecompass/qa/GroundedAnswerGenerator.java:8-13`
- Evidence: `src/main/java/dev/codecompass/qa/RagContextBuilder.java:73-84`
- Impact: A malicious repository can attempt to influence model behavior, including through comments that mimic instructions.
- Recommendation: Clearly delimit source data, preserve the instruction hierarchy, add prompt-injection evaluation fixtures, and avoid sending sensitive repositories to external providers unless users explicitly opt in.

### Medium — Frontend production build is not integrated with Maven

The frontend build is separate from Maven and generated static assets are ignored by Git.

- Evidence: `frontend/vite.config.js:17-20`
- Evidence: `.gitignore:10-11`
- Evidence: `pom.xml:21`
- Impact: A clean deployment that runs only `mvn package` can create a backend JAR without the frontend assets.
- Recommendation: Add a Maven frontend-build plugin or CI build stage that runs `npm ci` and `npm run build` before packaging.

### Medium — Indexed source is stored in plaintext with no tenancy boundary

The keyword index stores full source chunks locally, and the vector store is also stored under `data/`.

- Evidence: `src/main/java/dev/codecompass/indexing/KeywordIndexStore.java:26-30`
- Evidence: `src/main/resources/application.yml:22-24`
- Impact: Host users or backups with access to the data directory can read indexed source. This is especially significant for private repositories.
- Recommendation: For hosted use, isolate storage by owner and repository, enforce access control, use encrypted persistent storage, and define deletion/retention behavior.

### Low — No automated backend tests or frontend linting

The Maven test lifecycle has no test sources, and the frontend package exposes no `lint` script.

- Evidence: `src/test/` is absent.
- Evidence: `frontend/package.json:6-9`
- Impact: Scanner behavior, index compatibility, retrieval ranking, API validation, and UI changes can regress without automated detection.
- Recommendation: Add focused unit tests for scanning, ignore precedence, index reuse, atomic failure behavior, and RAG grounding. Add ESLint and run lint/build/test in CI.

### Low — API errors are not normalized

The controller exposes index and answer operations without centralized exception handling.

- Evidence: `src/main/java/dev/codecompass/api/AssistantController.java:21-29`
- Impact: provider, scanner, and persistence failures can return inconsistent server errors, which makes the UI and integrations harder to handle predictably.
- Recommendation: Add a `@RestControllerAdvice` that returns stable JSON error bodies and appropriate status codes for validation, limits, unavailable providers, and index failures.

## Deployment Readiness

The current design is appropriate for a trusted local, single-user environment. Before hosting it for users who submit repository links, resolve the critical and high-severity issues, then add authentication, provider-controlled cloning, isolated background jobs, per-repository indexes, and durable persistent storage.
